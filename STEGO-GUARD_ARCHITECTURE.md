# STEGO-GUARD — Архитектура системы
## Версия документа: 1.0 | Статус: Утверждено к реализации

---

## 1. Видение и назначение

Stego-Guard — система защиты цифровых документов от подделки, несанкционированного
редактирования и утечек. Первый прикладной домен — верификация сканов избирательных
протоколов и иных юридически значимых документов.

Система решает три задачи:
1. **Внедрение скрытой метки** (watermark) в документ при его выпуске/публикации,
   связывающей файл с его содержимым и контекстом (ID документа, ID участка,
   хэш содержимого).
2. **Проверку подлинности** любой копии документа: извлечение метки и сверка
   с реальным содержимым файла.
3. **Локализацию вмешательства**: построение тепловой карты зон документа,
   которые были изменены после внедрения метки.

Ключевой принцип: метка не видна человеку, устойчива к пересылке через
мессенджеры, почту, публикации в соцсетях (JPEG-сжатие, ресайз, скриншоты),
и при этом позволяет точно сказать — «файл изменён, и вот где именно».

---

## 2. Архитектурный обзор

Система построена как три независимо разворачиваемых сервиса, общающихся
по строго определённым контрактам:

┌──────────┐   HTTP/REST   ┌──────────────┐   gRPC (внутр. сеть)   ┌─────────────┐
│ FRONTEND │ ────────────► │ API GATEWAY  │ ─────────────────────► │ ML-SERVICE  │
│ React/TS │ ◄──────────── │     Go       │ ◄───────────────────── │   Python    │
└──────────┘               └──────────────┘                        └─────────────┘
                                │
                                ▼
                         ┌──────────────┐
                         │  PostgreSQL  │  (реестр документов, аудит)
                         └──────────────┘

**Принципы:**
- Тонкий клиент: вся бизнес-логика на бэкенде.
- Go-гейтвей — единственная точка входа наружу (HTTP). ML-сервис недоступен
  извне, живёт только во внутренней сети.
- Контракт между сервисами — Protocol Buffers (gRPC), единый источник правды.
- Каждый сервис масштабируется независимо.
- Состояние хранится вне контейнеров (БД, объектное хранилище).

## 3. Компоненты системы

### 3.1. Frontend (React + TypeScript + Mantine v7)

Назначение: пользовательский интерфейс для операторов и аудиторов.

Состав:
- Главная страница с переключателем режимов «Защита» / «Проверка».
- Зона загрузки документа (drag-and-drop) с клиентской валидацией формата.
- Экран результата защиты: хэш документа, кнопка скачивания защищённой копии.
- Экран результата проверки: вердикт (подлинный / изменён / метка не найдена),
  процент BER, отображение тепловой карты с регулировкой прозрачности.
- История проверок (таблица с пагинацией).

Свойства: SPA, сборка Vite, деплой как статика за nginx. Состояние — локальное
(useState), без глобального сторов, библиотека компонентов Mantine.

### 3.2. API Gateway (Go 1.21+)

Назначение: приём HTTP-запросов, валидация, аутентификация, маршрутизация,
кэширование, оркестрация обращений к ML-сервису, запись в БД.

Модули:
- HTTP-слой (Fiber): маршруты /api/v1/embed, /api/v1/verify, /api/v1/documents.
- Валидация загрузок: магические байты (не расширение!), лимит размера,
  допустимые MIME-типы, антивирусная проверка (опционально, поздняя фаза).
- gRPC-клиент к ML-сервису: пул соединений, таймауты, ретраи с backoff.
- Хэширование: SHA-256 содержимого документа (payload метки строится
  на основе этого хэша + ID пользователя/участка).
- Аутентификация: JWT (роли: operator — защита документов, auditor — проверка,
  admin). В фазе 1 — без авторизации (внутренний контур).
- Персистентность: PostgreSQL (реестр: ID документа, оригинальный хэш,
  кто/когда защитил, результат проверок).
- Аудит: лог всех операций embed/verify с метками времени.

Свойства: stateless (можно реплицировать), graceful shutdown, метрики
(Prometheus-эндпоинт), структурированные логи.

### 3.3. ML-Service (Python 3.10+, PyTorch, PyWavelets, OpenCV)

Назначение: стеганографическое кодирование и верификация. Ядро системы.

Модули:
- DWT/DCT-слой: разложение изображения на субполосы LL/LH/HL/HH (PyWavelets),
  обратное восстановление. Payload внедряется в средне- и высокочастотные
  субполосы (LH/HL/частично HH) — там визуально незаметно и устойчиво к JPEG.
- Нейросетевой кодек: Encoder (внедряет битовый payload в вейвлет-коэффициенты)
  и Decoder (извлекает payload). Обучаются совместно: loss = точность
  извлечения payload + незаметность (L1/LPIPS к оригиналу) + стойкость
  (аугментации-атаки на лету).
- Payload-формат: заголовок (магия, версия, длина) + SHA-256 документа +
  ID пользователя/участка + CRC. Итог ~ 300+ бит.
- Верификация: извлечение payload, расчёт BER (bit error rate) относительно
  ожидаемого хэша, сверка хэша с реальным содержимым файла.
- Heatmap: попиксельная карта расхождений между извлечёнными и ожидаемыми
  битами, наложенная на сетку изображения → PNG-маска зон вмешательства.
- Сервисный слой: gRPC-сервер, реализующий контракт из proto-файла,
  работа с сырыми байтами, без диска (in-memory пайплайн).

Свойства: GPU-опционально (инференс CPU-терпим для документов), модель
загружается один раз при старте, batch-обработка для массовой верификации.

### 3.4. Хранилища

- PostgreSQL: реестр документов и аудит.
- Объектное хранилище (MinIO/S3-совместимое): защищённые копии документов
  и heatmap-изображения. В фазе 1 — файловая система с привязкой к БД.
- Redis (опционально, фаза 3): кэш результатов повторных проверок
  (идентичный файл → идентичный вердикт).

## 4. Двухрежимная логика

### Режим 1 — Защита (Embedding)
Вход: документ (PNG/JPEG) + ID пользователя/участка.
Шаги:
1. Gateway: валидация файла, расчёт SHA-256.
2. Передача байтов изображения + payload-структуры в ML-сервис.
3. ML: DWT-разложение → нейросетевой Encoder внедряет payload
   (хэш + ID + служебные поля) в LH/HL-субполосы → обратное DWT → кодирование
   в итоговый формат.
4. Gateway: запись в БД (ID документа, оригинальный хэш, метаданные),
   сохранение защищённой копии.
Выход: защищённый файл для скачивания + карточка с хэшем.

### Режим 2 — Проверка (Verification)
Вход: произвольный файл, претендующий на подлинность.
Шаги:
1. Gateway: валидация, расчёт SHA-256 содержимого.
2. Передача байтов в ML-сервис.
3. ML: извлечение payload нейросетевым Decoder → расчёт BER →
   сравнение извлечённого хэша с хэшем полученного файла →
   построение heatmap зон расхождения.
4. Gateway: интерпретация вердикта по порогам BER, запись в аудит.
Выход: JSON-вердикт + heatmap-картинка.

### Дерево вердиктов
- BER ≈ 0 и хэши совпали            → ПОДЛИННЫЙ
- Метка извлечена, BER в допуске,
  хэш не совпал                     → ИЗМЕНЁН (heat map показывает зоны)
- Метка извлечена, BER высокий      → ИЗМЕНЁН / атака на метку
- Метка не обнаружена               → НЕ ЗАЩИЩЁН СИСТЕМОЙ (не верифицируем)

## 5. Протоколы взаимодействия

### 5.1. Внешний интерфейс (Frontend ↔ Gateway)
- REST/JSON поверх HTTP/1.1.
- Загрузка файлов: multipart/form-data.
- Ответы проверки: JSON с полями вердикта, BER, совпадения хэша,
  heatmap (base64 или ссылка на объектное хранилище).
- Ошибки: единый формат { error: code, message }.

### 5.2. Внутренний интерфейс (Gateway ↔ ML-Service)
- gRPC поверх HTTP/2, бинарные фреймы, потоковая передача.
- Передача сырых байтов изображения (bytes) — без промежуточных файлов.
- Два RPC:
  - EmbedWatermark(image, payload_meta) → (watermarked_image, status)
  - VerifyDocument(image) → (ber, hash_match, authenticity, heatmap_image)
- Дедлайны: 30 сек на запрос; отмена по контексту при обрыве HTTP-клиента.

### 5.3. Контракт как источник правды
- Описание сообщений и сервисов — в proto/stego.proto.
- Генерация кода: Go (protoc-gen-go, protoc-gen-go-grpc),
  Python (grpcio-tools).
- Любое изменение API — только через изменение proto с регенерацией
  обеих сторон. Ручная правка сгенерированного кода запрещена.

## 6. Модель данных

Таблица documents:
- id (uuid), оригинальный sha256, формат, размер,
- id пользователя/участка (из payload), дата защиты, путь к защищённой копии.

Таблица verifications:
- id, document_id (nullable — файл мог быть чужим), sha256 проверяемого файла,
- вердикт, BER, дата, IP/пользователь инициатора.

Таблица users (фаза 2): логин, хэш парола, роль.

## 7. Безопасность

- Транспорт: внутри контур — TLS-терминация на reverse-proxy (фаза продакшена).
- Аутентификация: JWT с ролями; ключи — в переменных окружения/секретах.
- Проверка файлов: магические байты, лимит размера, запрет исполняемых типов.
- Целостность: весь аудит подписывается временными метками; хэши дублируются.
- Payload защищён от чтения посторонним: формат не публикуется,
  без обученной модели извлечение невозможно в разумное время.
- Rate limiting на эндпоинтах проверки (анти-брутфорс верификации).

---

## 8. Развёртывание и эксплуатация

- Docker, мультистейдж-сборки; Docker Compose — локально и для пилота.
- Сервисы: frontend (nginx), gateway (alpine-образ Go), ml-service
  (образ на базе python-slim + системные зависимости OpenCV/PyWavelets).
- Конфигурация — переменные окружения, без хардкода.
- Логи: JSON-логи в stdout, сбор через Docker logging driver.
- Метрики: Prometheus + Grafana (фаза 3); health-check эндпоинты.
- Бэкапы: PostgreSQL — ежедневный дамп; объектное хранилище — репликация.

---

## 9. Масштабирование и отказоустойчивость

- Gateway: stateless → горизонтальное масштабирование за балансировщиком.
- ML-Service: репликация N+1 с балансировкой round-robin на gRPC-уровне;
  GPU-ноды для интенсивных нагрузок.
- Очередь задач (NATS/RabbitMQ) — для массовой пакетной верификации
  (например, проверка тысяч протоколов после выборов) без блокировки API.
- Graceful degradation: при недоступности ML-сервиса проверки
  ставятся в очередь, пользователю — статус «в обработке».

## 10. План реализации (фазы)

Фаза 1 — Контракт и скелет:
- proto/stego.proto; структура репозитория; venv;
- gRPC-сервер Python (заглушки Encoder/Decoder с базовым DWT-пайплайном);
- Go-гейтвей с HTTP-загрузкой и проксированием;
- фронтенд-скелет с двумя режимами.

Фаза 2 — ML-ядро:
- обучение Encoder-Decoder (датасет документов/сканов);
- стойкость к JPEG/ресайзу/кропу; расчёт BER; heatmap;
- интеграционные тесты end-to-end.

Фаза 3 — Production:
- PostgreSQL, JWT-аутентификация, аудит, MinIO;
- Docker Compose оркестрация, метрики, rate limiting;
- пакетная верификация через очередь.

---

## 11. Риски и ограничения

- Стойкость к сильному сжатию (соцсети пережимают) — требует баланса
  ёмкости payload и незаметности; контролируется обучением и тестами.
- Сканирование с потерями: распечатка и повторное сканирование документа
  необратимо разрушает нейросетевую метку → такие копии детектятся
  как «изменённые», что корректно для модели угроз.
- PDF-документы: в фазе 1 поддерживаются растровые форматы; PDF — через
  рендеринг страниц (фаза 3).
- Юридическая значимость вердикта: система — инструмент экспертизы,
  не самостоятельное доказательство (требует методики и аттестации).

## Приложение А. Глоссарий

- DWT — дискретное вейвлет-преобразование (разложение на частотные субполосы).
- DCT — дискретное косинусное преобразование.
- BER — bit error rate, доля ошибочно извлечённых битов метки.
- Payload — полезная нагрузка метки (хэш + ID + служебные поля).
- Heatmap — тепловая карта зон вмешательства в документ.
- LL/LH/HL/HH — субполосы вейвлет-разложения
  (низкие/смешанные/смешанные/высокие частоты).
